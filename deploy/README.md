# Закрытый подсервис на VPS pilchai

Репозиторий `Mist3s/market_parser`, ветка `main`. Push запускает проверки, сборку target `api`
и отправку образа `ghcr.io/mist3s/market_parser:<полный SHA>` в GHCR. Отдельный шаг вызывает
по SSH только `deploy <SHA>`. `workflow_dispatch` с `tag` разворачивает существующий образ
для отката; запуск разрешён только из `main`.

## Сеть и данные

Compose-проект `market-parser` независим от проекта `pilchai`. Общая сеть `pilchai-mktlink`
создана с `--internal`; в неё включены только API pilchai и mktlink. Адрес потребителя:
`PILCHAI_MKTLINK_BASE_URL=http://mktlink:8000`. PostgreSQL pilchai к общей сети не подключается.
У парсера нет `ports`, маршрута nginx или публичного домена. Отдельная сеть `egress` сохраняет
исходящий доступ к маркетплейсам. `external: true` в Compose означает, что сеть управляется
вне проекта, а не доступ из интернета.

Работает один API-процесс, без forge, браузера и Redis: лимиты 256 МиБ, 0,5 CPU и 128 процессов.
SQLite хранится в `/var/lib/mktlink/data`, владелец `10002:10002`. Пересоздание контейнера
и откат не удаляют данные. `mkt init-db` выполняется отдельным шагом перед запуском.
Контейнер работает без root, с read-only корневой ФС и без Linux capabilities.

## Первичная установка

Администратор переносит каталог `deploy/` на VPS и выполняет `bash deploy/bootstrap`.
Команда создаёт сеть, каталог данных, пустой файл настроек `/opt/mktlink/mktlink.env` (600)
и устанавливает `/usr/local/bin/mktlink-deploy`. Повтор не затирает настройки или базу.

В репозитории GitHub нужны secrets:

| Имя | Значение |
| --- | --- |
| `DEPLOY_HOST` | адрес VPS pilchai |
| `DEPLOY_USER` | `root`, доступ ограничен отдельным ключом |
| `DEPLOY_SSH_KEY` | отдельный закрытый ключ этого репозитория |
| `DEPLOY_KNOWN_HOSTS` | проверенный SSH host key VPS; не `ssh-keyscan` при каждом деплое |

Публичная половина ключа добавляется отдельной строкой в `/root/.ssh/authorized_keys`:

```text
restrict,command="/usr/local/bin/mktlink-deploy" ssh-ed25519 <public-key> mktlink-actions
```

Этот ключ не открывает shell, SFTP, PTY или проброс портов. Скрипт принимает `deploy <SHA>`,
`rollback <SHA>`, `local <SHA>` и `status`; SHA проверяется на сервере. GHCR token передаётся
через stdin и хранится в отдельном временном Docker config только на время запуска.
`local` предназначен для заранее загруженного образа того же фиксированного репозитория.

Настройки поставщиков задаются администратором в `/opt/mktlink/mktlink.env`, ключи не входят
в образ, исходники и secrets сборки. Для Ozon и Яндекс.Маркета нужен `MKTLINK_SCRAPEDO_TOKEN`;
без него процесс может быть здоров, но разбор возвращает отказ. Наличие API-ключей в таблице
`api_key` включает авторизацию mktlink; в этом случае соответствующий ключ нужно задать
в серверном `PILCHAI_MKTLINK_API_KEY` и перезапустить потребитель.

Для Ozon в этой поставке задаётся `MKTLINK_SCRAPEDO_SHORTEN_VIA=clck`: полная ссылка сначала
сокращается, затем передаётся в scrape.do. При отказе сокращателя прямой URL не отправляется.
Яндекс.Маркет через сокращатель не проходит. После изменения `mktlink.env` из `/opt/mktlink`
выполните `docker compose --env-file .image up -d --wait mktlink`: `.image` содержит тег образа.
Отказы поставщика возвращаются как 503 с `meta.reason=provider_domain_disabled`,
`provider_error` или `shortener_unavailable`, без необработанного исключения и тела поставщика.
Входящие короткие ссылки Ozon и Я.Маркета тоже разворачиваются через scrape.do.
Ozon сначала проходит настроенный сокращатель; конечный URL берётся из заголовка
поставщика. Бюджет `/v1/resolve` — до 30 с, клиент должен отправлять
`max_wait_ms=30000` и ждать не меньше 30,5 с. Первый вызов может выполнять рендеринг
и расходовать кредиты; повторный берёт URL из постоянного кэша. Отказы поставщика
не переключают запрос на прямое соединение с маркетплейсом. Сокращателю доступно
до 4 с в пределах общего бюджета; из времени scrape.do вычитается фактическая длительность.

## Порядок запуска и проверка

1. Выполнить bootstrap и настроить secrets Actions.
2. Выпустить mktlink через push в `main`: Actions дождётся healthcheck, проверяющего API и SQLite.
3. Выпустить бэкенд pilchai с общей сетью и внутренним URL. Его deploy-скрипт также создаёт
   сеть при отсутствии. Оба deploy-скрипта используют `/run/lock/pilchai-deploy.lock`.
4. С VPS проверить HTTP из контейнера потребителя:

```bash
docker exec pilchai-api-1 python -c 'import urllib.request; print(urllib.request.urlopen("http://mktlink:8000/readyz", timeout=5).status)'
docker inspect market-parser-mktlink-1 --format '{{json .HostConfig.PortBindings}}'
```

Вторая команда должна показать пустое значение, первая — `200`. Это проверяет соединение,
но не успешность извлечения товара: её проверяют отдельной пользовательской ссылкой.
Браузер пользователя обращается только к pilchai.

## Отказ и откат

Неуспех инициализации схемы или healthcheck возвращает прежние образ и Compose-конфигурацию.
При первой неудачной установке контейнер останавливается, данные сохраняются. Предыдущий
успешный выпуск записан в `/opt/mktlink/.image.previous`. Ручной откат — запуск Actions с его SHA.
Автоматический откат не восстанавливает SQLite: будущие изменения схемы должны оставаться
совместимыми с предыдущим API; перед несовместимой миграцией нужна отдельная копия базы.

CI проверяет тесты, ShellCheck, сборку API без браузерных зависимостей и запуск контейнера
в изолированной Docker-сети. Smoke test проверяет DNS, ответ API, отсутствие опубликованных
портов и повторный старт с тем же томом, без обращений к магазинам.
